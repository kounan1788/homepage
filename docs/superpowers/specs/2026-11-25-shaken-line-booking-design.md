# 車検のLINE予約 設計書

2026-11-25 作成。ユーザーと相談して決めた内容と、こちらで決めた内容（【判断】と記す）をまとめる。

## 1. 目的
お客様が車検ページの受け入れ状況カレンダーで日付を選び、電話をせずにLINEで車検予約を申し込めるようにする。
お店はLINE公式アカウントのチャットで返事をして予約を確定する。確定した予約には、前日にLINEで自動のお知らせを送る。

背景：先に作った「車検満了日リマインダー」（満了日の2ヶ月前にLINEでお知らせ）から予約までを、LINEの中で一続きにしてお客様の手間を減らす。

## 2. 目標・対象外・失敗とみなすこと
- 目標
  - 〇（受付可能）の日から、スマートフォンで数タップで申込ができる
  - 申込内容がスプレッドシートに記録され、お店にメールで届く（受け漏れゼロ）
  - お客様からの申込文がLINEのチャットに届き、お店はそこで返事して確定できる
  - お店がシートに「確定日」を入れた予約には、前日にLINEでお知らせが届く
- 対象外（今回は作らない）
  - 自動で予約を確定すること（カレンダーは日ごとの〇△×だけで、台数の管理がないため）
  - 予約の変更・キャンセルの画面（チャットで受け、スタッフがシートを直す）
  - 予約件数に応じてカレンダーの〇△×を自動で変えること
  - 受付完了をお店からLINEで送ること（お客様自身の送ったメッセージが控えになるので、送信数を使わない）
- 失敗とみなすこと（動いていてもダメな状態）
  - 申込が届いたのに、お店が気づけない（シート・メールのどちらにも残らない）
  - 確定していない予約や、キャンセルされた予約に前日のお知らせが届く
  - 同じ予約に前日のお知らせが2回届く
  - お客様が「予約が確定した」と誤解する画面や文言（申込の時点では未確定）

## 3. 前提・制約
- **自動送信はできない**：お客様の名前でトークにメッセージを送る `liff.sendMessages()` は、LINEのトーク画面から開いたLIFFでしか使えない。サイトから開くと外部ブラウザ扱いになり、使えない（LINE公式資料で確認済み）。そのため、最後はトーク画面を「申込文が入力済み」の状態で開き、お客様に送信を押してもらう（`https://line.me/R/oaMessage/{ベーシックID}/?{本文}`）。
- お店からは、お客様が一度チャットにメッセージを送らないと返事ができない。上の申込文がそのきっかけになる。
- お店から送るメッセージ（プッシュ）は月の無料上限に数えられる。今回増えるのは、確定した予約1件につき前日のお知らせ1通。
- 前日のお知らせを送るには、お客様が公式LINEの友だちである必要がある（リマインダーと同じ確認を入れる）。
- 以前の車検カレンダーの設計メモには「予約機能は作らない」とあったが、今回その方針を変える（ユーザー確認済み）。
- まだ必要な値：LINE公式アカウントの**ベーシックID**（`@` から始まるID）。
- このフォルダはgitリポジトリではないため、設計書のコミットはしていない。

## 4. 検討した作り方
| 案 | 中身 | よい点 | 弱い点 |
|---|---|---|---|
| 1. 申込文を入力済みにしてトークを開く | 予約ボタンの行き先を `oaMessage` のURLに変えるだけ | 作る量が最小。送信数ゼロ | 入力漏れが起きる。記録がチャットにしか残らない。前日のお知らせを送れない |
| **2. LIFFフォーム（採用）** | LINEログイン付きフォームで入力 → シートに記録・お店にメール → 入力済みのトークを開く | 入力漏れを防げる。記録が残る。前日のお知らせを送れる | 作る量が多い。LINEの管理画面での設定作業が要る |
| 3. 案1で始め、必要になったら案2 | 段階的に進める | 最初が早い | 前日のお知らせが後回しになる |

ユーザーは案2を選び、前日のお知らせも今回から入れることにした。

## 5. お客様の流れ
```
車検ページのカレンダーで〇の日を押す → 「LINEで予約する」
  → LIFFの予約フォームが開く（希望日は押した日が第1希望に入った状態）
  → LINEログイン（未ログインの場合）・友だち確認（友だちでなければ追加を案内）
  → 入力：第1希望日（必須）・第2希望日（任意）・お名前（必須。LINEの表示名を初期値）
          車種（必須）・ナンバー下4桁（任意）・ご連絡事項（任意）・個人情報の同意（必須）
  → 「申し込む」
  → 完了画面：「お申し込みを受け付けました。まだ予約は確定していません。
              続けて下のボタンからLINEで申込内容を送信してください。当店から確定のご連絡をします。」
  → 「LINEで送信する」ボタン → トーク画面が開き、申込文が入力済み → お客様が送信
```
申込文の例：
```
【車検予約の申込】受付番号 B-1234
第1希望：12月10日（水）
第2希望：12月12日（金）
お名前：港南 太郎
車種：N-BOX（ナンバー 1234）
※このまま送信してください
```

## 6. お店の流れ
1. 申込があると、店舗アドレス（`kounan.lease@gmail.com`。お問い合わせフォームの送り先 `app/actions/sendEmail.ts` の `TO_ADDRESS` と同じ）にメールが届き、シート「bookings」に1行増える（状態は空欄＝未確定）。
2. お客様からチャットに申込文が届く。お店はチャットで返事をして日程を確定する。
3. 確定したら、シートのその行の **確定日** に日付を入れる（必要なら **来店時刻** も）。
4. 前日の17時に、確定日が翌日の行へLINEでお知らせが送られる。前日の17時より後に確定した予約には自動では届かないので、チャットの返事の中で案内する。
5. キャンセル・日程変更：確定日を消す／書き換える。消せば前日のお知らせは送られない。お知らせを送ったあとで別の日に書き換えた場合は、新しい日の前日にもう一度送る（同じ確定日に二度は送らない）。
6. お客様が申込文を送らなかった場合でもシートとメールには残るので、電話などで連絡する。

## 7. 構成（今ある仕組みの使い回し）
- **予約フォームのページ**：新しいページ（例 `/shaken-booking`）。リマインダーの `app/shaken-reminder/` と同じ作り（ページ本文はサーバー描画、フォームは `ssr: false` で読み込み、LIFFの初期化・ログイン・友だち確認）。
- **サーバー処理**：新しいServer Action。`registerShakenReminder.ts` と同じ守り方をする（IDトークンをLINEで検証して userId を得る・入力の検証・ハニーポット・IP連投制限・共有シークレットを付けてGASへ中継）。
  - 希望日は、サーバー側でも受け入れ状況（`lib/shakenCalendar/service.ts` の `getAvailability()`）を読み、選べる日かどうかを確かめる。
- **GAS**：リマインダーのGAS（`docs/gas/reminder.gs`）に追加する。同じスプレッドシートに「bookings」シートを作る。
  - 【判断】別のGASにしない理由：チャネルアクセストークン・共有シークレット・毎朝9時のトリガー・月次レポートをそのまま使えるため。`doPost` は届いた本文の種類（リマインダー登録／予約申込）で処理を分ける。
  - 申込を受けたら、シートに書き込んだあとで店舗アドレスへメールを送る（MailApp）。【判断】書き込めたときだけメールが出るように、GAS側で送る。
  - 【判断】前日のお知らせは、リマインダーの `dailyCheck()` には混ぜず、別の関数（例 `bookingDailyCheck()`）と別のトリガー（毎日17時台）で動かす。リマインダーの処理を組み直さずに済み、9時より後に確定した翌日の予約も拾える。
  - 確定日が明日の行へ前日のお知らせを送る。送ったら送信日時と「通知した確定日」を記録する。判定は「確定日が明日」かつ「通知した確定日が確定日と違う（または空）」。これで同じ日に二度は送らず、日程を変えた場合は新しい日に送り直せる。送れなかったら店舗へまとめてメール（リマインダーと同じ）。
  - 【判断】試運転用のフラグは予約専用に分ける（例 `BOOKING_DRY_RUN`）。リマインダーがすでに本番で動いていても、予約側の試運転のためにリマインダーの送信を止めずに済む。`BOOKING_DRY_RUN` の間は、お客様に送らず、送る予定の一覧を店舗へメールする。
  - GASのコードを貼り替えるときは、本番で入れてあるトークン・スプレッドシートID・シークレットを空の値で上書きしないよう、手順書に手順を書く（設定値の行は残して、追加部分だけを足す）。
  - 月次レポートに、前日のお知らせの送信件数も含める。
- **カレンダー**：`components/ShakenAvailabilityCalendar.tsx` の〇の日の「LINEで予約する」ボタンの行き先を、予約フォーム（日付つき）に変える。
- **公開スイッチ**：【判断】カレンダーと同じく環境変数で切り替える（例 `NEXT_PUBLIC_SHAKEN_BOOKING_ENABLED=true`）。オフの間は、今まで通り友だち追加リンク（`LINE_URL`）に飛ぶ。

### シート「bookings」の列（案）
受付日時／受付番号／第1希望／第2希望／氏名／LINE userId／車種／ナンバー下4桁／ご連絡事項／**確定日**（スタッフ入力）／**来店時刻**（スタッフ入力・任意）／前日通知日時／通知した確定日／送信結果／備考

## 8. 細かい決めごと（【判断】）
- **選べる日**：明日以降で、カレンダーの表示期間（当月＋3か月）の中の〇の日だけ。△の日は今のカレンダーで「お電話で確認」としているので、その扱いは変えず、予約フォームでも選べないようにする（フォームでは「△の日はお電話でご相談ください」と案内）。×の日・定休日は選べない。
  - ※前回のやりとりでは「△の日も申込可」と書いたが、今のカレンダーの考え方（△＝電話で確認）に合わせて、△は選べないことにした。△も申込できるようにしたい場合は変更する。
- **受付番号**：シートの行とチャットの申込文を結びつけるための短い番号。重ならないようにGASで振る。
- **パソコンで開いた場合**：スマートフォンのLINEで開くよう案内し、予約フォームのURLと電話番号を出す。QRコードは、生成のために新しいライブラリが必要になるため今回は出さない（実装計画の段階で変更）。
- **前日のお知らせの中身**：日付・来店時刻（入っていれば）・持ち物（車検証・自賠責保険証明書・納税証明書など）・お店の電話番号。文面はお店に確認して決める。
- **前日のお知らせを送る時刻**：前日の17時台（予約専用のトリガー）。定休日でも送る。17時より後に確定した翌日の予約には届かない（チャットで案内する）。
- **同じお客様の複数申込**：リマインダーと違い、上書きせずに毎回1行追加する（複数台・日程の出し直しがあるため）。
- **個人情報**：プライバシーポリシーに、予約申込で預かる内容（希望日・車種・ナンバー・ご連絡事項・LINEの識別子）と目的を追記する。

## 9. お店側の準備（管理画面での作業）
- LINE Developers：予約フォーム用のLIFFアプリを追加する（エンドポイントは予約フォームのページ）。スコープはリマインダーと同じ（`openid`・`profile`）。
- LINE公式アカウント：ベーシックIDを確認する。チャットをオンにしておく（返事をするため）。
- Vercel：LIFF ID・公開スイッチなどの環境変数を追加して再デプロイする。
- GAS：追加したコードを貼り付けて保存し、ウェブアプリを新しいバージョンで公開し直す。
- 運用手順書（スタッフ向け）を書く：確定日の入れ方、キャンセルのしかた、申込文が届かないときの対応。

## 10. 作る人に任せること
- ファイル名・コンポーネントの分け方・型の置き場所
- フォームの見た目（既存のリマインダーフォームとそろえる）
- 受付番号の形式
- 申込文の細かな文言（失敗とみなすことに反しない範囲で）
- テストの書き方（既存の vitest を使う）
